# The Ask sits at the bottom of the middle column

Status: design, 2026-09-16. Follows `docs/specs/2026-09-15-one-ask-scoped.md` (shipped as #311),
which this spec changes in one place only: **where the Ask lives and how a topic reaches it**.
The request contract, the chips-from-`applied_scope` rule and the scope copy are unchanged.

## 0. Why

The user rejected the shipped entry point after using it on dev (2026-09-16):

1. "Ask about this topic" sits under the topic title in the right detail — "这个位置太不明显，用户
   不会把注意力放在那".
2. Clicking it scrolls the middle column to the very bottom, "失去了继续检查 topic 的连续性".
3. The day Ask is also at the bottom of the middle column's scrolling content, so reaching it at all
   means scrolling past the whole day.

All three are position problems, not behaviour problems.

## 1. Target

A **docked Ask bar** pinned to the bottom of the middle column:

* always in view — it is outside the scrolling content, so nothing is ever "scrolled to";
* its scope **follows the selection**: no selection → the day; a topic selected in the right detail
  → that topic;
* one row of scope chips + one input row. Suggestions appear when the input is focused, not before.

```
middle column (topic list keeps its scroll position)
┌───────────────────────────────┐
│ 09:04  PC Certificate…     ●  │ ← selected
│ 09:06  Emergency evacuation    │
│ …                              │
├───────────────────────────────┤ ← dock: outside the scroll container
│ [Thu 3 Sep · UC PK · Ben ×] [Topic: PC Certificate… ×]
│ ✉ Ask about this topic…    [↑] │
└───────────────────────────────┘
```

Asking expands the conversation **upward, over the list** (an overlay anchored to the dock), so the
list neither moves nor reflows. Closing the conversation leaves the list exactly where it was.

## 2. Decisions taken (user, 2026-09-16)

| Question | Decision |
|---|---|
| Entry point | The docked bar. `Ask about this topic`, `pinTopicAsk` and the focus-nonce scroll are **removed**. |
| Switching topics | The bar follows the selection and **does not clear the conversation**. It inserts a divider message instead. Day / owner / site changes still clear. |
| Default shape | One chips row + one input row. Suggestions on focus only. |
| Mobile (≤767px) | **Out of scope.** The web is desktop-only (user, 2026-09-16); do not spend design or verification effort on phone widths. |

### 2.1 Open decision, defaulted in this spec

The aggregated **site view** currently mounts no Ask, which the user accepted while the Ask lived
in the page body. With a dock the absence becomes conspicuous — the bar would simply be missing on
the view a site manager lands on. **This spec proposes docking there too**, scoped to `date + site`
(no author). If the user vetoes, the site view keeps no dock and `hasAsk`-style suppression stays.

## 3. Shell change — a `Footer` slot

`MiddleColumn` (`scripts/app-shell.js`) renders a flex column: a 56px header (`flexShrink: 0`) and
a content area (`flex: 1; overflowY: auto`). Add a **third child**, `flexShrink: 0`, rendered from
`PAGES[route].Footer` — the same lookup already used for `.Provider` (`app-shell.js` ~1369),
`.Middle` (~998) and `.Right` (~1087). A route without a `Footer` renders nothing and keeps today's
layout byte for byte.

The Footer receives the same props the Middle gets (route, selectedItem, onSelect), so it can read
the selection without new plumbing.

## 4. Timeline wiring

* `TimelineAskProvider` keeps `askContext` / `setAskContext`. `askFocusNonce`, `requestAskFocus`,
  `hasAsk`, `setHasAsk` and `AskPresence` are removed — the dock is always present where a page
  registers a Footer, so nothing needs to publish its presence.
* The dock's context is derived, not clicked:
  * no topic selected → `{date, siteId, siteName, authorFolder, authorName}` (unchanged
    `askContextForDay`);
  * a topic with a `topic_row_id` selected → the same plus `{topicRowId, topicTitle}`;
  * a topic without one (meeting topics) → the day context, unchanged.
* `TopicAskButton` and `pinTopicAsk` are deleted along with their tests.

## 5. `AskChat` changes

* New `variant: 'dock'`: chips row, input row, suggestions rendered only while the input has focus
  or the conversation is open; the message list renders in an overlay above the bar with its own
  `max-height` and its own scroll.
* **Conversation reset, revised.** Today one effect keyed on
  `[context.date, context.siteId, context.authorFolder, context.topicRowId]` clears `msgs`
  (`ask-chat.js` ~682). Split it:
  * `date` / `siteId` / `authorFolder` change → clear, exactly as now (and keep the generation bump
    and the deferred-resend handling);
  * `topicRowId` change alone → **keep the messages** and append one divider entry
    (`role: 'divider'`) reading `Now asking about: <topic title>`, or `Now asking about the whole
    day` when a topic is deselected. The generation bump still happens, so a late answer from the
    previous scope is still dropped.
* Chips, `applied_scope` enforcement marks, basis lines, the widen button and `requestBodyFor` are
  unchanged.

## 6. What must not regress

* The request body per state (day / topic / unscoped), verified live on dev 2026-09-16.
* Chips reflect `applied_scope`, never the request.
* A late answer from a previous scope is dropped.
* `tests/ask-timezone-and-basis.test.js` stays unchanged and green.

## 7. Tests

Driven (the existing `mountAsk` harness):

1. Selecting a topic adds `topic_row_id` to the next request **and keeps prior messages**, with one
   divider appended.
2. Deselecting adds a divider and drops `topic_row_id`.
3. A `date` change still clears the conversation.
4. A late answer from the pre-switch scope is not appended after a topic switch.
5. Suggestions are absent until the input is focused.

Source-level: the dock renders as a sibling of the scroll container, not inside it (a regression
here silently restores the scroll-to-bottom problem).

## 8. Non-goals

Phone layouts; changing the palette Ask; changing any backend contract; the site-day Ask beyond
§2.1.
